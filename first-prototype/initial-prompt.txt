In this project we will explore the concept of voronoi diagrams as extended from finite point set inputs in n dimensions, to finite simplicial complex inputs in n the same dimensions, with an initial foray into the 2D behavior and the ultimate goal of a robust and performant implementation for 3D situations. First attempt at a formal definition of this generalized voronoi diagram: It is supposed to partition space. Each point in space is classified by the set of input simplices which attain the minimum distance from that point to the input simplicial complex. Points with the same classification constitute a cell of the outut complex. Thus cells of the output complex are given by systems of quadratic constraints. Let's first focus on the generic case, in which nice assumptions can be made about the relationship between the number of equations and the dimensionality of the cell. In this generic case it should be easy to avoid bugs in which one fails to partition space; we can return to edge cases (e.g. discretized circle) later, although if we are lucky they will mostly work already in v1. Draw a little house with an open chimney as a first example mesh consisting of a handful of line segments in 2D. Let's use the julia language. Combinatorially speaking the output should consist of a certain set of subsets of the input simplicial complex. Thus if the input is considered as an element of P(P(VertexIdx)) [P means powerset, which is inherently finite here], then the output is an element of P(P(P(VertexIdx)), where the vertex indices refer to a pointcloud that is provided in floating point (or possibly in rational numbers for early versions of the code). It would be nice if we could write our own shader for this output complex - somehow it would feel more right if it would be able to stand on its own legs in this way. But pragmatically we could also discretize it into an auxiliary simplicial complex or simplex soup for rendering purposes. In principle such discretization could lead to negatively oriented elements if we are unlucky and/or careless; a policy about how to handle that possibility will necessarily follow some experimentation. Anyways, let's say that for starters we have the ability to compute the output complex in generic situations and to draw it. This then sets the stage for later applications where we may do queries on the output complex connectivity and geometry as well as select regions of it interactively. For a first version (v1) in 2D we should have the ability to hover over a cell and it should show the set of constraints that define it. And for a fun demo which gets the idea across and conveys the behavior of this concept, why not also allow the user to edit the input complex interactively and observe the changes to the output in real time? Let's then also have some presets: house, monkey, tree, droplet.

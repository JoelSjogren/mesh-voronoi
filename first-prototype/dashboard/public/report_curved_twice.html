mesh-voronoi-nd — a curved bisector crossing one edge twice

One-off investigation report, generated from a live run of the actual construction code (not a mockup) — see the live dashboard for ongoing test status.

update multi-crossing is now handled (task #26)

The gap this report documents — a curved bisector crossing a single existing edge twice, which used to be a hard error — is fixed. clip_top_cell_2d! (`N=2`) now walks a cell's whole boundary, splits each edge at 0, 1, or 2 crossings with the new bisector (exactly the "generic (0 or 2)" count this report's own step 4/5 show is the real, typical outcome here, not a rare coincidence), and reassembles the resulting same-side runs into their own cells, each closed by its own fresh arc. The general-purpose (non-`N=2`, or more-than-2-crossings) fallback still only supports a single crossing per edge and errors otherwise — a scope limit of that specific code path, not a claim that more crossings are somehow non-generic.

Everything below is the original report, kept as-is (including the now-stale <pre> error text below, which the code no longer produces) since it's still the clearest walkthrough of why the double crossing happens and what the correct output looks like — step 5's brute-force ground truth is exactly what clip_top_cell_2d! now constructs directly.

Summary (original report)

clip_by_hyperplane! assumes a bisector crosses any single existing edge at most once. That's true for a straight (linear) bisector, but a genuinely curved one — a parabola, from comparing a point against a segment's interior — can dip into a region and back out again, crossing one edge twice. When that happens (at the time this report was written) the code detected it and raised a clear error rather than silently assembling a wrong cell: 

clip_by_hyperplane!: an edge with both endpoints on B's side is nonetheless crossed
by the bisector internally -- outside the generic (at most one crossing per edge)
case handled so far

Setup

One fixed segment, {0,1}: (−2,0) → (2,0). Then a second segment, {2,3}, from (0,1) upward — in two variants:

variantv2v3what it shows
symmetric(0,1)(0,2)an exact 3-way tie — now fixed
generic(0,1)(0.5,2)the real gap — still open

Both variants share the same essential shape (a short segment poking up from a point just above the long horizontal one) — only v3's x-coordinate changes, from exactly 0 (perfectly aligned) to 0.5 (nothing special about it at all).

Step 1 — segment {0,1} alone

Base case, shared by both variants: segment {0,1}'s own perpendicular cuts split the bounding box into its three regions (beyond each endpoint, plus the interior strip).

Step 2 — symmetric variant: segment {2,3} added now fixed

With v3=(0,2), segment {2,3} is exactly vertical, directly above where segment {0,1}'s endpoint-vs-interior boundary sits. This makes point 2=(0,1) exactly equidistant from three things at once, at two points (red stars, marked at (±1,1)): segment {0,1}'s interior, its own point-2 feature, and segment {2,3}'s interior. That's a genuine exact tie, not a floating-point coincidence — verified directly by evaluating all three distance formulas there and getting exactly 1.0, three times over. This construction used to hard-error; it now succeeds, resolving the tie via a fixed, deterministic rule.

Step 3 — generic variant: segment {2,3}'s own cuts inserted

Same idea, but v3=(0.5,2) — segment {2,3} now leans to the right, with nothing special about its position relative to segment {0,1} at all. Pure refinement so far, before any comparison; the red-outlined cell is about to be compared against point 2, and is about to hit the bug.

Step 4 — the bisector crosses this cell's edge twice bug

Comparing the red cell's current winner (segment {0,1}'s interior) against point 2 gives a parabola (blue curve) — visibly dipping below the cell's own diagonal edge and crossing it twice (blue × marks), at two genuinely distinct points (0.618, 0.691) and (−1.618, 1.809) — not a repeated root, not float noise, a real double crossing. Both of that edge's own endpoints are on the same side of the parabola, so clip_by_hyperplane!, which only knows how to split an edge at a single crossing point, raises the error above instead of guessing.

Step 5 — why: the true region needs two cuts

Brute-force ground truth (no clipping algorithm involved, just evaluating both distance formulas directly): segment {0,1}'s interior (green) is closer almost everywhere, but point 2 (purple) wins a lens-shaped intrusion that pokes in and back out through one edge — the same two × marks as step 4. Correctly carving this out needs the edge split into three pieces at two crossing points, not the one piece at one crossing point the current code assumes.

Where this points

Generalizing clip_by_hyperplane!'s edge-processing to support more than one crossing per edge (splitting into 3+ pieces along a single original edge, in whichever order the crossings occur) would close this gap for the 2D case; the general-N case needs the same idea one dimension up (a curved bisector surface meeting an existing face more than once).

mesh-voronoi-nd — a cell's territory can have a hole (task #39)

One-off investigation report, generated from a live run of the actual construction code (not a mockup) — see the live dashboard for ongoing test status.

fixed the construction now supports multiply-connected cells

Found by a random stress test built while chasing a different bug (task #51): inserting a second, crossing segment near an existing arrangement of points reliably produced "cyclic_boundary_walk: boundary edges don't form a simple cycle", a hard crash deep inside construction. Root cause: one point's own remaining Voronoi territory can end up entirely enclosed inside a segment's own dominance region — a genuine hole, not a bug in the sense of corrupted data. cyclic_boundary_walk assumed every cell's own boundary was exactly one simple closed loop of edges; a cell with a hole has that loop plus a second, entirely disjoint one (the hole's own boundary), and the walk had no way to notice and simply gave up partway through.

Fixed by generalizing the walk (now cyclic_boundary_walks, plural) to decompose a cell's edges into all of its simple cycles instead of assuming one, and teaching the clip routine that builds new cells (clip_top_cell_2d!) to treat every loop but the largest (by bounding-box area) as a hole: carried through unchanged and reattached to whichever resulting piece geometrically contains it, rather than reprocessed for crossings — a hole's own splitting, if the new bisector actually reaches it, is already being discovered independently by whichever cell that hole itself belongs to, since every live cell is clipped against the same new bisector on its own.

Verified against the exact repro below (full trace, not just "it doesn't crash"), plus the whole test suite (26,505 tests) and a 60-trial randomized stress test of two-segment arrangements: zero cyclic_boundary_walk failures remain, versus every one of those trials hitting it before the fix.

still open, lower stakes polygon_vertices_2d (used only for rendering, e.g. the plain-fill images on this very page) is a separate copy of the same single-loop walk and has the identical gap — a cell with a hole still can't be tessellated for display. Not fixed here, for the same reason tessellate_curve wasn't fixed alongside task #43's own construction-side fix: nothing in the core algorithm depends on it anymore, so it's a display-quality question now, not a correctness one. Step 1 and 2's images below work around it directly (outline-only fallback for any cell with a hole) rather than relying on it.

Setup

The exact repro found by the stress test: one long segment plus 3 points (the same arrangement used for task #51's own "bug7" preset), then a second segment crossing near point 4's own region, then a 5th point landing inside what used to be point 4's own tiny leftover territory. Built through the library's own insert_entry!, the same path multi_complex/the interactive demo use.

Step 1 — a hole forms, silently, from perfectly ordinary insertions

After the first segment and 3 points, then a second segment crossing near point 4: point 4's own remaining region (red outline) has shrunk down to a small lens shape, and it turns out to sit entirely inside segment 6–7's own territory (green) — nothing else touches its boundary. This is a completely ordinary outcome of the construction rules, not a special case anyone deliberately engineered; the bug was that nothing downstream expected it. At this point the complex is already in this state, and everything still works — insert_entry! itself never needed to notice the hole. The crash only happens on the next insertion, once something needs to walk this cell's own boundary.

Segment 6–7's own cell (the one with the hole) is what's being clipped when this throws: its subcells list contains both its real outer boundary and the hole's own 4 edges, all mixed into one flat list. The walk consumes the 11 outer edges, closes back to its own start vertex, and then has 4 edges left over with nowhere left to attach — the exact signature of "this is actually two separate loops," not "this data is corrupted."

Step 3 — after the fix

The same insertion now succeeds. The new point (black dot) lands inside the old hole and splits it correctly into two pieces — point 4's own further-shrunk remainder (cyan) and the new point's own sliver (white outline; itself drawn outline-only here because, by coincidence, that fresh cell also ends up with its own hole elsewhere in the diagram after the same-label merge pass — a second, independent instance of the exact scenario this fix handles, not specially arranged for this report). Segment 6–7's own surrounding cell keeps referencing both resulting pieces as its own two holes, unchanged from before this insertion touched it at all.

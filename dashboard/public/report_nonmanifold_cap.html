mesh-voronoi-nd — a genuine tie point breaks label consistency across a face

One-off investigation report, generated from a live run of the actual construction code (not a mockup) — see the live dashboard for ongoing test status. This page replaces an earlier report about the same repro's own non-manifold-cap bug, which is now fixed.

partially fixed propagating the walk's own side instead of re-deriving it per edge

The face-level inconsistency below (face 1382's own edges disagreeing) is fixed: clip_flat_face_3d!/clip_curved_face_3d! now carry the side of whichever vertex the boundary walk most recently arrived at forward to the next edge, instead of independently re-asking the shared label for every edge's own two endpoints. Past the very first edge, a crossing is the only thing allowed to flip the side — exactly what the surrounding code already claimed to do, just not quite what it implemented. A cached edge's own already-committed side still wins if the two ever disagree (nothing already baked into the complex gets silently reinterpreted).

This exact repro now gets past face 1382 cleanly, then fails a fourth way — the same kind of disagreement, one level up: a different face, reached from a different top-level cell that also happens to touch the same near-tied vertex, still disagrees with what this walk decided. The fix is correctly scoped to one face's own walk; it was never going to reconcile the same vertex across independent walks in different cells — that's the same shape of problem as an already-known, separately-tracked open issue (sweep_topology_check's "shared boundary represented differently on its two sides" finding). Three-segment stress success: 49/150 → 50/150, zero label mismatches maintained. Small, real, and honestly not the whole story.

Step 3 — the two vertices the odd edge connects

Zoomed in on the crimson edge from Step 2 and its two endpoints. The orange vertex evaluates to -9.9×10⁻¹⁴ against the third segment's own bisector, restricted to this face's plane — indistinguishable from exactly zero: a genuine tie, this vertex sits (numerically) right on the boundary between the two sides. The black vertex evaluates to 8.23 — nowhere near zero, completely unambiguous.

What's actually wrong

Every edge's own side comes from asking a shared, precomputed label — "is this vertex already known to be on the A side?" — for each of its two endpoints. When both endpoints agree, the edge just uses that. When they disagree and no actual crossing explains why, there's a fallback: trust whichever endpoint's own raw evaluation is less ambiguous (bigger in magnitude), and let that decide the edge's side, overriding the shared label locally. That's exactly what happened to the crimson edge in Step 2: its two endpoints' shared labels disagreed, no crossing was found between them, so it deferred to the black vertex's own unambiguous 8.23 over the orange vertex's own essentially-zero value — a reasonable, deliberate call in isolation.

The bug is what happens next. That correction is local to the one edge that made it — it's never written back to the shared label the orange vertex carries everywhere else. A different edge touching that same orange vertex (part of the same face's own boundary, cached from an earlier, sibling face's own independent clip) never re-examines anything; it just trusts the shared label directly, and gets the opposite answer. Both resolutions are locally defensible. They can't both be used on the same face's own boundary walk without it falling apart, which is exactly what the "edges disagree on side" error is catching — correctly, just with no way to recover once it's happened.

This is a real, close cousin of an already-known open issue in this codebase (a "shared boundary represented differently on its two sides" defect sweep_topology_check already flags at both N=2 and N=3, tracked separately) — the same underlying shape: a genuine near-degenerate configuration resolved two different, locally-reasonable ways by two different pieces of code that never compare notes.

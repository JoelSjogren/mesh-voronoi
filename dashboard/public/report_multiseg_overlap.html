mesh-voronoi-nd — multi-segment overlap bug, step by step

One-off investigation report, generated from a live run of the actual construction code (not a mockup) — see the live dashboard for ongoing test status.

update the root cause is fixed — and so is the case once misdescribed as "non-generic"

The overlap illustrated below was traced to edge_crossings parametrizing an existing boundary edge as the straight chord between its two endpoints, even once that edge is actually curved (true since a segment's own bisector can be a parabola). Fixed by having the crossing computation solve against the edge's own stored curve instead, whenever it has one. The exact three-segment scenario below (steps 1–4) no longer produces an overlap — verified directly: 0 overlapping cells among all 19 live cells after this same refinement step, and it's now a permanent regression test.

also now fixed a related, harder case this report originally called out as unimplemented: a comparison between two features whose bisector is itself curved, touching a cell whose boundary is also already curved from an earlier step — in general a quadric–quadric intersection (up to 4 points via Bezout). This report's own original wording described the rejected case as outside "generic case only" limits, as if it were some rare coincidence being deliberately excluded — that framing was wrong, and worth flagging explicitly: this configuration is exactly as generic as the overlap bug this whole report is about (an open, nonzero-measure set of configurations produces it, not an equality-constrained special case like two parallel segments). It was a genuine gap in what was implemented, not a deliberately-excluded degenerate case. It's since been resolved exactly (quadric_quadric_crossings): every stored curved edge in this codebase's feature model is a point-vs-line bisector sharing one feature with any other curve it's compared against, which reduces the general quadric- quadric problem to two ordinary line-vs-quadric calls instead of the full degree-4 case.

Summary (original report)

Inserting three segments (or a point after several segments) one at a time can leave two stored cells geometrically overlapping — a real invariant violation of the construction, not a floating-point rounding issue. It's masked whenever the lower-numbered overlapping cell happens to be found first during point-location; it only becomes visible once that cell is later superseded (split away) by a further insertion, revealing a duplicate underneath.

works a single segment (curved point-vs-segment bisector) — cross-validated with 0 mismatches across 13,000+ grid points.
works multiple segments that are far apart / never interact closely.
broken a third simplex whose own dividing lines have to refine a cell that already carries curved boundary structure from an earlier comparison.

The scenario below reproduces it with the smallest configuration found so far: three segments and one query point, none of them touching or crossing.

Setup

Three segments, inserted in this order:

  • segment 2: (2.3, 1.1) → (3.6, 0.7)

Query point (the red star in every image): (1.106, 1.121) — correctly closest to segment 2's near endpoint (2.3, 1.1), distance² ≈ 1.425.

Step 1 — segment 1 alone

Base case: segment 1 is the only thing inserted so far, so its own perpendicular cuts split the whole bounding box into its three own regions (beyond each endpoint, plus the interior strip). The query point starts out inside segment 1's interior region — correct for now, since nothing else exists yet to compete with it.

Step 2 — segment 2's own lines (pure refinement)

Before segment 2 is compared against anything, its own two perpendicular cuts get inserted everywhere they reach — a label-preserving refinement, not a relabeling. Every region should still carry whatever label it had before this step.

Step 3 — segment 2 compared against segment 1 correct

Segment 2 is now compared feature-by-feature against whichever of segment 1's features currently owns each region. Where segment 2 wins, the cell gets clipped and relabeled. The query point is correctly reassigned here: it's now inside segment 2's near-endpoint region (light blue), matching the oracle.

Step 4 — segment 3's own lines bug appears

Segment 3's own perpendicular cuts are inserted next — still meant to be pure refinement, touching only region shapes, not labels. But comparing this image to Step 3: the dark green (segment 1 interior) region has already started reaching further up and to the right than it should, toward where segment 2's light-blue territory was. The two red-outlined cells here were found, independently, to both contain the query point — point-location just reports whichever one it finds first in storage order, so the overlap itself doesn't throw an error yet.

Step 5 — segment 3 compared against existing winners wrong result

Segment 3 is now compared against whatever each region's current winner is. For the query point's location, that "current winner" is segment 1 (because of the Step 4 overlap the comparison stage doesn't know about) instead of segment 2. The comparison proceeds correctly given that premise, but the premise was already wrong: the query point ends up permanently labeled as segment 1's interior. The oracle says it should be segment 2's near-endpoint region — compare directly against Step 3, where that region (light blue) visibly reached the query point and now no longer does.

Where this points

The refinement step (clip_by_plane_preserving_label!, reused from the main clip routine via two symmetric dummy points whose bisector is exactly the target plane) assumes splitting one cell at a time, independently, is always safe. That's true when every cell is a simple flat-edged polygon sharing boundaries with exactly the neighbors its own subcell list already knows about — guaranteed in the points-only case. It stops being guaranteed once a cell's own boundary already includes a curved edge from an earlier comparison: refining it can produce a new piece whose shape doesn't correctly account for what a neighboring cell (reached only through that curved edge) already claims. Fixing this needs the refinement step to be aware of curved-boundary adjacency, not just re-use the flat-hyperplane clip as-is.

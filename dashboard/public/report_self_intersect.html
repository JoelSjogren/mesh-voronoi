mesh-voronoi-nd — a cell's own boundary self-intersects (task #43)

One-off investigation report, generated from a live run of the actual construction code (not a mockup) — see the live dashboard for ongoing test status.

update the core algorithm no longer tessellates at all

The "most likely location" flagged below was confirmed exactly right, then fixed at the root rather than patched: find_containing_cell (and its BVH counterpart) no longer approximates a curved boundary as a sampled polyline at all. It now solves for exactly where each edge crosses a ray from the query point, directly against the edge's own stored quadric equation, and decides whether that crossing is genuinely on the edge's own bounded arc by projecting onto the curve's natural single-valued axis — the eigenvector of the curve's own quadratic part for its nonzero eigenvalue, which turns out to need no eigendecomposition at all: for the rank-1 matrices every stored curved edge in this codebase actually has, the matrix's own first row already is that eigenvector. This is exactly the "analytic, not sampled" fix the tessellation approach was missing — the arc's own turning point (its blind spot) is no longer special-cased away, it's simply never assumed monotonic in the first place.

Verified directly against the exact repro below: 0 mismatches across 19,366 grid points checked against the brute-force oracle in the region that used to render as a broken bowtie, and find_hover_target resolves cleanly there with no error. Cell 243's own stored structure (see Step 3) was correct all along — the bug was entirely in a downstream consumer approximating it, never in construction itself.

still open, lower stakes tessellate_curve itself (used only for rendering: polygon_vertices_2d, plot_cells_2d, the images on this very page) still uses the old "whichever coordinate varies more" convention and can still visibly self-intersect when drawn. Not fixed here — it's a display-quality issue now, not a correctness one, since nothing in the core algorithm depends on it anymore.

Summary (original report)

A live top cell's own boundary, walked via polygon_vertices_2d, can come out as a polygon that geometrically self-intersects — two of its own non-adjacent edges cross each other in the plane. This is distinct from (but a sibling of) the other failure mode the same function can hit, "cell X's boundary edges don't form a simple cycle" (the edges don't even connect into a cycle at all) — that variant was hit directly by a real user session this week and is now caught defensively in the interactive demo's own hover code (a debugging aid degrading gracefully, not crashing the session) rather than fixed at the source. This report is about the self-intersection variant specifically, still open, tracked as task #43.

still open no fix attempted here — this report's job is to pin down where the bug actually lives, which turned out to be more specific and more surprising than expected.

Setup

8 random points, inserted first, then one long segment drawn diagonally across the whole canvas — deliberately close to how the user's own crash report described it ("lots of points and then a big long segment running diagonally across the screen"). Minimized from an original 25-point repro down to 8 by simply dropping points from the end of the list and re-checking; it stayed reproducible all the way down. Built through the library's own insert_entry!, the same path multi_complex/the demo use.

Step 1 — 8 points alone

Base case: a plain power diagram of 8 points, G1-only. Every cell here is convex by construction — there's no way for a flat-bisector-only diagram to produce a self-intersecting polygon, so this step is only here to confirm the starting state is unremarkable.

Step 2 — the diagonal segment is added bug appears

One segment inserted, crossing several existing cells. Cell 243 (red outline, labeled "point 4 wins here") renders as a visibly broken bowtie shape near (7,1.5) — exactly what a self-intersecting polygon looks like when handed to a plain fill routine. (Note the similar-looking rough patch near (−3,1) too — a different, nearby construction wrinkle, not investigated here; this report follows cell 243 specifically.)

Step 3 — cell 243's own boundary, up close

Cell 243's stored structure is completely unremarkable: exactly three subcells (orange dotted lines) — two straight edges and one curved one, forming a clean, valid graph cycle. The blue solid line is polygon_vertices_2d's own reconstruction, which tessellates the curved edge into 17 sample points (numbered) for rendering. Points 3–12 trace a smooth arc bulging up and to the right, peaking around (7.3, 4.1) — then points 12–18 plunge down through the middle of the shape, crossing straight back through the 3→12 arc and the 1→3 edge on the way to point 1. That crossing is the self-intersection.

Where this pointed, and what confirmed it

Two hypotheses were checked and ruled out before finding the real one, which was then confirmed exactly (not just plausibly) and fixed for every core-algorithm consumer:

  • Not a malformed subcell list. Cell 243 has exactly three subcells, and they genuinely form a simple cycle vertex-to-vertex. The self-intersection is entirely a property of how the curved edge gets sampled into points for rendering, not of the underlying graph structure.
  • Not a near-degenerate line-pair slipping past is_line_pair's tolerance (the mechanism behind the multi-crossing/line-pair work earlier this session). Checked directly: the curve's own det3 degeneracy measure is 0.1485, about 1650× above the detection threshold — nowhere near degenerate. Its eigenvalues are exactly {0, 1}, the textbook signature of a genuine point-vs-line parabola (provably a single smooth branch, not two disconnected ones), not a pair of lines.
  • Confirmed: tessellate_curve's own parametrization loses track of the curve. Every individual sample point is genuinely on the curve (all 17 agree with the stored quadric's own equation to ~1e-14) — so it's not "solving the wrong equation" at any single sample, it's that the sequence doesn't trace one continuous path. tessellate_curve walks whichever coordinate (x or y) varies more between the two endpoints; for this arc, that heuristic loses continuity partway through, because the arc's own turning point (its vertex, where neither raw coordinate stays monotonic) falls between the two endpoints being sampled — exactly the condition a "walk one coordinate" scheme can't handle, confirmed by construction, not just observed.

The general fix: every curved edge this codebase actually stores is a genuine parabola (a line-vs-line bisector is always two straight lines instead, handled separately by clip_by_line_pair! since the multi-crossing work earlier this session — never stored as one curved edge). A parabola's own quadratic part M is always rank 1 (one zero eigenvalue), and for such a matrix the eigenvector of its nonzero eigenvalue is M's own first row whenever det(M)=0 — no eigendecomposition needed. Projecting onto that direction gives a single-valued parameter for the entire curve, turning point included, unlike either raw coordinate. find_containing_cell (and its BVH counterpart) now use this directly: for each boundary edge, solve exactly where it crosses a ray from the query point (substituting into the edge's own stored equation, not approximating it as a polyline first), and confirm each crossing is genuinely on that edge's bounded arc by checking whether its projection onto the curve's own natural axis falls between the two endpoints' projections. No sampling, no polygon, nothing to self-intersect.

tessellate_curve itself (rendering only) could use the same natural-axis parametrization to stop producing self-intersecting approximations too — not done here, since nothing in the core algorithm depends on it anymore and it's now a display-quality question, not a correctness one.

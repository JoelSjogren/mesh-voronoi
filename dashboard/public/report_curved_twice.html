mesh-voronoi-nd — a curved bisector crossing one edge twice

One-off investigation report, generated from a live run of the actual construction code (not a mockup) — see the live dashboard for ongoing test status.

update the "generic variant" below is fixed too

This report's own table (below) called the generic variant (v3=(0.5,2), no special alignment at all) "the real gap — still open" even after the symmetric variant's own double-crossing was fixed. It's fixed now. The root cause turned out to be subtler than "more crossings than expected": clip_top_cell_2d! decided how many cuts to make on an edge by comparing its two endpoints' own (possibly symbolic_tiebreak'd) sides, and errored whenever a genuinely generic configuration's strict interior crossing count didn't match what that comparison implied — e.g. "1 interior crossing while both endpoints agree" is not an exotic higher-crossing-count case, it's an ordinary single crossing paired with one endpoint that happens to sit (numerically) exactly on the new bisector itself, whose arbitrary tie-broken side doesn't reflect the true local sign. Fixed by deriving every resulting piece's side purely by alternating from the first endpoint's own side across however many strict interior crossings actually exist (0 through the Bezout ceiling of 4, for two genuine conics) — never consulting the second endpoint's own side at all, since it's exactly the value that can't be trusted here. See test_segments.jl's own "clip_by_hyperplane!: curved bisector crossing one edge once while both endpoints agree on side (generic variant)" test, which reproduces this report's own generic-variant numbers exactly and cross-validates against 25000+ grid points with zero mismatches.

update multi-crossing is now handled (task #26)

The gap this report documents — a curved bisector crossing a single existing edge twice, which used to be a hard error — is fixed. clip_top_cell_2d! (`N=2`) now walks a cell's whole boundary, splits each edge at 0, 1, or 2 crossings with the new bisector (exactly the "generic (0 or 2)" count this report's own step 4/5 show is the real, typical outcome here, not a rare coincidence), and reassembles the resulting same-side runs into their own cells, each closed by its own fresh arc. The general-purpose (non-`N=2`, or more-than-2-crossings) fallback still only supports a single crossing per edge and errors otherwise — a scope limit of that specific code path (never actually reached at `N=2`, since every real call site here clips a genuine top-level cell), not a claim that more crossings are somehow non-generic.

Everything below is the original report, kept as-is (including the now-stale <pre> error text below, which the code no longer produces) since it's still the clearest walkthrough of why the double crossing happens and what the correct output looks like — step 5's brute-force ground truth is exactly what clip_top_cell_2d! now constructs directly.

Summary (original report)

clip_by_hyperplane! assumes a bisector crosses any single existing edge at most once. That's true for a straight (linear) bisector, but a genuinely curved one — a parabola, from comparing a point against a segment's interior — can dip into a region and back out again, crossing one edge twice. When that happens (at the time this report was written) the code detected it and raised a clear error rather than silently assembling a wrong cell: 

clip_by_hyperplane!: an edge with both endpoints on B's side is nonetheless crossed
by the bisector internally -- outside the generic (at most one crossing per edge)
case handled so far

This report was rewritten after two rounds of feedback. First: back it with an actual, deterministic unit test instead of just describing it in prose — done (test_segments.jl, "clip_by_hyperplane!: KNOWN GAP -- curved bisector crossing one edge twice errors instead of silently misassembling"). Second: the original reproduction used ugly, random floating-point coordinates that made it easy to mistake this for a rare exact-coincidence fluke. It's not — this page now shows a small, mostly-round-number configuration, and a second, deliberately less special variant of it, to make clear the underlying issue is generic (an open, nonzero-measure set of configurations produces it), not a special-case artifact of some exact coincidence.

fixed, separately a genuinely different bug surfaced by the first (symmetric) configuration below: an exact tie between three features at a single point, which used to hard-error ("vertex exactly on the bisector -- degenerate case not yet handled"). That's now resolved deterministically via symbolic_tiebreak (pick a side by a fixed, consistent rule, exactly like the standard "simulation of simplicity" technique for robust geometric predicates) — not by chance, and not related to the multi-crossing gap this report is actually about, even though the same small example happens to touch on both.

now fixed handling a bisector that genuinely crosses one edge more than once — see the update above.

Setup

One fixed segment, {0,1}: (−2,0) → (2,0). Then a second segment, {2,3}, from (0,1) upward — in two variants:

variantv2v3what it shows
symmetric(0,1)(0,2)an exact 3-way tie — now fixed
generic(0,1)(0.5,2)the real gap — now fixed

Both variants share the same essential shape (a short segment poking up from a point just above the long horizontal one) — only v3's x-coordinate changes, from exactly 0 (perfectly aligned) to 0.5 (nothing special about it at all).

Step 1 — segment {0,1} alone

Base case, shared by both variants: segment {0,1}'s own perpendicular cuts split the bounding box into its three regions (beyond each endpoint, plus the interior strip).

Step 2 — symmetric variant: segment {2,3} added now fixed

With v3=(0,2), segment {2,3} is exactly vertical, directly above where segment {0,1}'s endpoint-vs-interior boundary sits. This makes point 2=(0,1) exactly equidistant from three things at once, at two points (red stars, marked at (±1,1)): segment {0,1}'s interior, its own point-2 feature, and segment {2,3}'s interior. That's a genuine exact tie, not a floating-point coincidence — verified directly by evaluating all three distance formulas there and getting exactly 1.0, three times over. This construction used to hard-error; it now succeeds, resolving the tie via a fixed, deterministic rule.

Step 3 — generic variant: segment {2,3}'s own cuts inserted

Same idea, but v3=(0.5,2) — segment {2,3} now leans to the right, with nothing special about its position relative to segment {0,1} at all. Pure refinement so far, before any comparison; the red-outlined cell is about to be compared against point 2, and is about to hit the bug.

Step 4 — the bisector crosses this cell's edge twice now fixed

Comparing the red cell's current winner (segment {0,1}'s interior) against point 2 gives a parabola (blue curve) — visibly dipping below the cell's own diagonal edge and crossing it twice (blue × marks), at two genuinely distinct points (0.618, 0.691) and (−1.618, 1.809) — not a repeated root, not float noise, a real double crossing. Both of that edge's own endpoints are on the same side of the parabola, so clip_by_hyperplane!, which only knows how to split an edge at a single crossing point, raises the error above instead of guessing.

Step 5 — why: the true region needs two cuts

Brute-force ground truth (no clipping algorithm involved, just evaluating both distance formulas directly): segment {0,1}'s interior (green) is closer almost everywhere, but point 2 (purple) wins a lens-shaped intrusion that pokes in and back out through one edge — the same two × marks as step 4. Correctly carving this out needs the edge split into three pieces at two crossing points, not the one piece at one crossing point the current code assumes.

Where this points

done generalizing clip_by_hyperplane!'s edge-processing to support any number of crossings per edge (splitting into as many pieces as needed along a single original edge, sides derived by alternation rather than by comparing the two endpoints against each other) closed this gap for the 2D case, for both the exactly-2-crossing and the single-generic-crossing-with-a-tied-endpoint variants above. The general-N case still needs the same idea one dimension up (a curved bisector surface meeting an existing face more than once) — not attempted yet, since 3D construction itself hasn't started. The interactive demo's "house" preset no longer needs its chimney position specially chosen to avoid this gap, now that both variants are fixed.

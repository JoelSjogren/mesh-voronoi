A layer at infinity for unbounded cells (planning report)

Written before any code exists for this — a mathematical analysis and implementation plan, not a bug report. See the bottom for status and next steps.

planning the problem

Every construction today starts from init_bbox_complex, an axis-aligned rectangle chosen by padding the input's own bounding box by an arbitrary margin. Every cell that's genuinely unbounded (its true territory extends to infinity in some direction) gets artificially truncated at this rectangle's edge instead — a rendering convenience, not a property of the diagram itself. The ask: replace this with something principled, where the added boundary is a real, labeled part of the output complex (an actual "this cell touches infinity here" fact you can query), not an arbitrary clip.

The proposed idea: a suitably scaled copy of the convex hull of the input can stand in for this boundary, with each added boundary edge labeled by whichever input vertex it's closest to (<V1,∞>), and each added boundary vertex labeled by the pair of input vertices whose bisector reaches it (<V1,V2,∞>). This report works out whether that's exactly right, finds one place where the literal reading of "scaled copy" fails, and proposes the corrected version.

1. The one fact that makes this tractable

Fix a direction (unit vector) u and look at the winner among a fixed set of bounded input features as you walk out along x = R·u with R → ∞. For any bounded set S (a point, a segment, in general any of this project's own feature validity regions restricted to a bounded piece of geometry):

sqdist(R·u, S) = R² − 2R·hS(u) + O(1), where hS(u) = supp∈S u·p (the support function of S)

because |Ru−p|² = R² − 2R(u·p) + |p|² and |p|² stays bounded while R→∞, so minimizing over p∈S reduces, at leading order, to maximizing u·p. Every feature's distance grows like R² with the same leading coefficient — the entire competition is decided by which feature has the larger O(R) correction, i.e. the larger support-function value. This is exactly why ordinary (point-set) Voronoi bisectors are straight lines with no curvature term surviving at infinity, generalized to this project's own richer feature set.

Two structural consequences fall out immediately:

  • A segment's support function equals its two endpoints'. h[a,b](u) = max(u·a, u·b) exactly, for every u — the max of a linear function over a segment is always at an endpoint. So at this leading order, a segment contributes nothing beyond what its own two endpoints already contribute.
  • Only the convex hull's own vertices can ever win. argmaxk hSk(u) is, by definition, exactly the classical support-function characterization of the convex hull of every input vertex — the vertex (or, on a measure-zero set of directions, tied set of vertices) extremal in direction u.

2. Points only: the normal fan

For a pure point set, this is the textbook picture, restated in this project's own vocabulary: the directions u partition into the convex hull's own normal cones — one per hull vertex Vi, the set of directions for which Vi alone maximizes u·Vi. Two adjacent normal cones meet along a single ray: the direction exactly perpendicular to hull edge ViVj, where Vi and Vj tie.

This is exactly the proposed labeling, read as a statement about directions rather than literal geometry: a normal cone (an angular range, i.e. a whole arc of the boundary-at-infinity) is labeled <Vi,∞>; the single ray where two adjacent cones meet is labeled <Vi,Vj,∞>. A hull vertex becomes a boundary edge (an arc of directions); a hull edge becomes a boundary vertex (one direction) — the labeling is dual to the hull's own combinatorics, matching what was asked to be verified.

found a real gap 3. Where literal convex-hull scaling breaks

The literal reading of "a suitable scaling of the convex hull" is: pick an origin O inside the hull, and map every vertex Vi → O + λ(Vi−O) for a huge λ. The natural hope is that scaled vertex λVi then sits inside Vi's own normal cone, so the scaled hull's own vertex/edge structure is the labeled boundary. This is false in general, even for a fully generic (non-degenerate, affinely-spanning) input.

Concrete counterexample: V1=(0,0), V2=(1,0.01), V3=(−100,100) (a valid, non-degenerate triangle — 3 affinely independent points, the generic case this project cares about). Take O close to V1 but strictly interior, e.g. O=(0.1,0.001). The scaling direction toward V1 is V1−O ≈ (−1,0). Checking which vertex actually maximizes u·Vk for u=(−1,0):

V3 wins, not V1 — even though the scaled point sits visually right where V1's own vertex should be. The scaled hull, rigidly scaled about a fixed interior point, can put a vertex in the wrong normal cone whenever the hull is skewed relative to the scaling origin. This isn't a degenerate/non-generic edge case — it's 3 ordinary points in general position; it's a property of the (origin, hull) pair, not of genericity.

the fix 4. Uniform edge offset, not scalar scaling

The failure is in how the hull is grown, not in the idea that the hull's own combinatorics are the right skeleton. The correct construction: push every hull edge's own supporting line outward, along its own outward normal, by the same large distance D (not by scaling every vertex by the same factor from one shared origin) — then re-intersect adjacent offset lines for the new vertices. This is ordinary convex-polygon offsetting (equivalently, eroding the complement / a Minkowski sum with a disk of radius D, taken to its polygonal limit).

Why this is exact: hull edge ViVj's outward normal n̂ is, by definition, perpendicular to Vi−Vj — which is exactly the true bisector-at-infinity direction between them (Section 2). Offsetting along that edge's own normal therefore encodes the correct direction by construction, for every edge, unconditionally — there's no shared origin whose placement relative to the whole hull can go wrong. Re-derived on the counterexample above: offsetting edge V3V1 and edge V1V2 outward and intersecting gives a new vertex strictly inside V1's own normal cone (the cone bounded by those two edges' own outward normals), for every D > 0 — no limit needed, no failure mode.

This is still "a suitable scaling of the convex hull" in spirit — same combinatorial skeleton, grown outward without bound — just offset by a distance rather than multiplied by a factor from a point. The two coincide only when the hull happens to have an inscribed circle tangent to every edge (equidistant offsetting = uniform scaling about that circle's center); offsetting is the version that's correct for an arbitrary hull.

5. Segments change the picture — but less than it first appears

With segments in the input (not just isolated points), does a segment's own interior feature ever have an unbounded cell reaching infinity, the way an endpoint can? Working through the same expansion restricted to the interior feature's own validity region (the perpendicular-foot-lands-on-the-segment slab): for any fixed direction u not exactly the segment's own normal, the validity slab's own angular width shrinks like O(1/R) as R→∞ — any fixed ray eventually exits it and falls back to endpoint territory. Exactly at u=±n̂ (the segment's own normal, held for every R), the interior's own distance grows like R² with coefficient exactly 1 (tied with any point's own leading order), and the next-order term decides it: the interior wins there iff that segment is itself an edge of the input's own convex hull (its own points have the largest projection onto n̂ among all input vertices).

So: only hull edges that are also real input segments get their own sliver of the boundary-at-infinity (a thin edge, not a bare tie point) — every other hull edge (implicit, connecting two vertices with no direct input segment between them) is a genuine <Vi,Vj,∞> tie, exactly as proposed. Concretely, for the offset construction (Section 4): a hull edge that's a real segment doesn't need any special geometric treatment in the offsetting itself (its offset line is exactly its own segment's own outward-offset supporting line, no different from an implicit edge's) — the distinction only matters for labeling that resulting boundary piece (as the segment's own interior reaching to infinity, rather than a plain endpoint tie) and, downstream, for whether the segment's existing interior feature's validity region should simply be understood to extend all the way to this new boundary rather than needing any new feature invented at infinity.

6. 3D, briefly

Section 1's argument is dimension-generic as written (nothing in the support-function expansion assumes N=2). The generic input this project cares about needs N+1 affinely independent vertices to affinely span N-dimensional space at all (a non-degenerate 3D pointcloud needs ≥4 points, not ≥3 — 3 points only ever span a plane). With that in place, the same duality holds one dimension up: hull vertices → boundary-at-infinity 2D facets (each one a solid angular region, labeled <Vi,∞>); hull edges → boundary-at-infinity 1D edges (an arc of tied directions between two adjacent vertices, <Vi,Vj,∞>, or a real segment's own sliver if that hull edge is an input segment); hull faces (triangles, for a simplicial hull) → boundary-at-infinity single points (<Vi,Vj,Vk,∞>, or a real input triangle's own facet reaching to infinity, by the same argument as Section 5 one dimension up). The offset construction (Section 4) generalizes unchanged: push every hull facet's supporting plane outward along its own normal by a fixed distance D and re-intersect.

7. Recommended implementation plan

  1. Compute the convex hull of the full input vertex set (every point feature's own location and every segment's two endpoints — Section 1's second consequence means interior-only geometry never contributes a new hull vertex).
  2. Build the offset polygon at a large, finite D (Section 4) — each hull edge's supporting line pushed outward by D along its own outward normal, adjacent offset lines intersected for the new vertices. This becomes the starting domain, replacing init_bbox_complex's padded rectangle.
  3. Feed it through the existing clip machinery unchanged. Because the offset polygon is, by Sections 1 and 4, already exactly the correct asymptotic-winner boundary (not an approximation that needs the real algorithm to "reach out" further), no new feature type or new clipping logic should be needed — every existing point/segment feature's own comparison against this boundary is the same comparison already implemented, just now bounded by a geometrically meaningful shape instead of an arbitrary rectangle.
  4. Label the boundary elements per Sections 2 and 5 once construction finishes: each boundary edge whose two neighbors are both plain vertices gets <Vi,Vj,∞> at the vertex between them and <Vi,∞> along its own length; a hull edge that's a real input segment gets its own thin labeled strip instead of a bare tie point.

Open questions to resolve during implementation, in picture-per-step order:

  • How large should the finite D be in practice? Needs to be large relative to the input's own diameter for the asymptotic argument's O(1)/O(1/R) error terms to be negligible, but not so large that the exact-predicate kernel's own floating-point conditioning suffers (coordinates spanning many orders of magnitude in the same complex). Should be measured empirically, not guessed.
  • Does merge_adjacent_same_label_cells! correctly recognize a hull vertex's own <Vi,∞> boundary piece as belonging to the same cell as Vi's own finite territory, so the two merge into one (correctly unbounded) cell rather than staying artificially split at the offset boundary?
  • Verify the offset-vs-scaling distinction (Section 3 vs 4) empirically on a deliberately skewed input, not just algebraically — confirm the naive approach visibly misplaces a cell and the offset approach doesn't.

implemented Step 1 — convex hull + offset boundary, standalone

convex_hull_2d (Andrew's monotone chain) and offset_polygon (Section 4, each hull edge's own supporting line pushed outward along its own normal by a fixed distance, then adjacent offset lines re-intersected) are both implemented and tested, including a test that reproduces the Section 3 counterexample numerically: confirms the naive scaled-vertex direction really does favor the wrong input point, and that the offset construction's own new vertex doesn't have that problem.
